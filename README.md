# CIVICX

CIVICX is a vanilla HTML/CSS/JavaScript prototype with a small Node.js server for optional AI and live-condition endpoints. Authenticated civic reports, report histories, and private attachments are stored in Supabase; demo metrics remain illustrative. Supabase is optional in this checkout and must be configured by the site owner.

## Run in VS Code

1. Install Node.js LTS.
2. Open this folder in VS Code and run `npm install` in the integrated terminal.
3. Keep the Gemini key in the server-only `.env` file as `GEMINI_API_KEY="..."`. The default model is the stable `gemini-3.5-flash-lite`; set `GEMINI_MODEL` only when choosing another model supported by your Google AI API key.
4. Run `npm start` and open `http://127.0.0.1:3000`.
5. Run `npm test` for the focused policy and privacy tests.

Use the Node server rather than a `file://` URL or Live Server: it serves the static app and same-origin `/api/chat` and `/api/ai/describe` endpoints. The map and external fonts require an internet connection.

## Page flow

- `index.html` is the public, full-screen landing page. Its background playlist starts automatically, stays muted for autoplay, and shows clearly labeled temporary artwork until the two actual videos are supplied.
- `dashboard.html` is the separate guest/account dashboard. Guest browsing does not save reports. Signed-in users can create account-linked reports and retrieve their saved report histories from Supabase; the map only shows records belonging to the signed-in account.
- `ai.html` is the dedicated CivicX AI page; signed-in users also get a floating assistant on the dashboard. It provides guidance and cannot file complaints or verify government status.
- Log in and sign up use a shared Supabase email OTP flow. New users choose a unique username only after verifying their email; existing profiles go straight to the dashboard. Supabase restores sessions across browser restarts, and signing out does not delete database reports.

## Shared Civic X theme

All website routes load `theme.css` for the shared dark navigation/footer, light content surfaces, yellow accent, rounded cards and controls, form states, and responsive motion. `theme.js` enables reduced-motion-aware section reveals. The public home page keeps its existing background-video playlist and Supabase email-code authentication while adding the tutorial, feature links, and Contact view. The Contact form opens the visitor's email app with a prepared message; the visitor must review and send it themselves. The contact links and address shown there are public details configured in `index.html`.

## Community setup (optional)

The community page is backed by Supabase, not browser-local mock conversations. To enable it:

1. Configure Supabase email OTP to use a 6-digit code. In **Authentication → Email Templates**, make both **Confirm signup** and **Magic Link** contain the numeric `{{ .Token }}` code and remove any `{{ .ConfirmationURL }}` link. New registrations and existing-user logins can use different templates. The app's `signInWithOtp` call does not set `emailRedirectTo` or another redirect URL; the message content comes from these Supabase templates.
2. Keep `.env` ignored and private. Use `GEMINI_API_KEY` for the server-only Gemini key; `SUPABASE_URL` and `SUPABASE_ANON_KEY` may be local environment variables or ignored `.env` entries. `.env.example` documents the names. Only the public anon key is exposed to the browser. `SUPABASE_SERVICE_ROLE_KEY`, `CIVICX_AUTHORITY_MASTER_KEY`, and `CIVICX_OWNER_MASTER_KEY` are server-only. Configure fresh random keys of at least 32 characters and put the owner account UUIDs in `CIVICX_OWNER_USER_IDS`; never put these values in browser code or chat. Keys previously shared in chat must be rotated before activation. The emergency-recovery key is not accepted by normal portal routes.
3. Before any database changes, run `supabase/diagnostics/civic_report_setup_preflight.sql` in the intended project's SQL Editor and review every result. Missing CivicX report tables are expected; any `STOP_*`, `STOP_MANUAL_POLICY_REVIEW`, incompatible schema, orphan data/object, or unreviewed foreign-key/policy change blocks deployment until investigated. Then create and verify a restorable backup of the database and relevant Storage objects. Apply the complete, self-contained `supabase/migrations/20261116120000_civic_report_schema_repair.sql` once. Do not first rerun the older report migrations or the community migration; this repair creates the report/tracking/authority structures and does not target `civicx-community`. Running SQL in the Dashboard does not automatically record a CLI migration-ledger row; document the manual application and reconcile migration history separately if the CLI is later introduced.
4. Apply `supabase/migrations/20261116170000_user_profiles.sql` in the intended project's Supabase SQL Editor to create the account profile table, uniqueness constraints, username availability function, and owner-only RLS. This is a schema-only change; it does not delete or rewrite civic records. Then reload `/community.html` and test with separate verified accounts. Moderator access must be granted by an administrator by inserting an account into `community_moderators`.
5. Apply `supabase/migrations/20261116180000_civicx_portal_service_role_read_grants.sql` after the report repair. It grants the server-only `service_role` read access to report, history, authority, and jurisdiction tables; citizens and browsers receive no new access. If the repair migration was already applied, apply this forward-only migration rather than rerunning the repair.
6. After the report repair and read-grants migration have been applied and verified, apply `supabase/migrations/20261117100000_civicx_owner_authority_portal.sql` to enable audited jurisdiction assignments through the Owner Portal. Configure rotated server keys and the owner UUID allowlist before testing `/authority.html` or `/owner.html`.
7. Apply `supabase/migrations/20261117110000_civicx_city_voting_authority_realtime.sql` after the report, community, and owner-portal migrations. It adds verified jurisdiction assignment for new reports, optional jurisdiction map centers, realtime report updates, directional community votes, and the `Pending` and `Cannot be Resolved` authority statuses. It does not modify or create Storage buckets or policies. Review the migration and back up the database before applying it.

Persistent discussions, civic reports, and private complaint tracking require the Supabase URL/anon key and their corresponding migrations. The pages report setup failures instead of claiming data was saved. The Supabase browser library is loaded from a CDN. Community photos are publicly readable; users should not upload faces, vehicle plates, exact addresses, or other identifying details.

The repair creates absent report/tracking objects, preserves rows, enforces account/report foreign keys, replaces CivicX-owned policies and triggers, and keeps report attachments private; it aborts on unexpected same-named relations, incompatible columns, unexpected report-table policies/triggers, orphaned rows/objects, or conflicting storage policies. It does not drop tables or delete rows. It changes the target bucket to private and restricts new uploads to JPEG files up to 10 MiB; review the preflight's bucket visibility and object inventory before approving that behavior. Running SQL in the Dashboard does not update the CLI migration ledger; reconcile the migration version only after the CLI is configured for and verified against the same project. Never manually insert a migration-ledger row.

## Landing videos

The landing page background player reads its ordered playlist from [`video-config.js`](./video-config.js). The civic-awareness slot is first (20 seconds) and the CivicX tutorial is second (40 seconds); playback advances automatically and loops back to the first slot indefinitely. Until media is supplied, `src: null` uses clearly labeled, timed placeholder artwork—not stock video. Replace each `src` with a path such as `assets/videos/civic-awareness.mp4` or an HTTPS media URL. Keep the clips at their configured durations; the player also enforces those durations if a file runs longer. No other page depends on the video sources.

## Civic report persistence and recovery

- Sign-in and sign-up use Supabase email OTP. Registration requires a verified email and a unique username; existing users with a profile go straight to the dashboard. Auth sessions use Supabase's persistent browser session storage with automatic token refresh. A report is accepted only when the user has an authenticated account, and its `user_id` is the permanent Supabase Auth UUID. The browser does not save submitted civic reports or their histories to local/session storage. Older reports left in browser storage by earlier prototype versions are not automatically imported, because their original account owner cannot be verified.
- The `civic_reports` table stores report details and current status. `civic_report_events` is append-only for clients and records submission, citizen disputes, reopening requests, citizen-recorded portal checks, trusted authority status actions, evidence additions, and evidence removals. Users can read only records for their own account; client-side users cannot alter report status, delete reports, or edit history.
- The server exposes `authority.html` for jurisdiction-scoped work and `owner.html` for global owner oversight. Every portal request requires a Supabase bearer session and a server-verified master key. Owner access also requires the authenticated UUID to be in `CIVICX_OWNER_USER_IDS`; the key alone never grants global access. Authority requests require an active allowlist row and active database jurisdiction assignments, which are applied server-side to report-list queries and rechecked for each detail, action, and attachment. The database RPC repeats the jurisdiction check before changing report status or resolution evidence. Supported `action` values are `status_update`, `reopen`, `resolution_evidence_add`, and `resolution_evidence_remove`; every action requires an audit note. The endpoints require `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and a rotated 32+ character server-only authority key. No service-role credential or master key is returned by `/api/public-config` or embedded in browser code.
- `GET /api/reports/:reportId/attachment` uses the same server-side session, active-allowlist, and database jurisdiction checks, looks up the attachment path from that report's database row (it never accepts a caller-supplied path), and returns a signed URL valid for 60 seconds with `Cache-Control: no-store`. The bucket stays private; ordinary citizens continue using owner-scoped Storage RLS. Out-of-jurisdiction reports and reports without a verified database jurisdiction are denied.
- Authority allowlisting and jurisdiction registry setup remain trusted administrative tasks. The repair deliberately seeds neither jurisdictions nor authority accounts. The dashboard's city options come from active `civic_jurisdictions` rows; the database trigger verifies the submitted jurisdiction key and display name against that registry before assigning it to a new report. It never trusts a city/key pair without an active database match. Existing reports are not automatically reassigned; an owner must verify their locations before assigning them. The Owner Portal's assignment RPC is service-role-only and records added/removed assignments in `civic_authority_admin_events`. Until a database assignment is active and a report jurisdiction is verified, authority access fails closed. Never grant browser clients access to authority or assignment tables.
- Set optional `center_latitude` and `center_longitude` on each `civic_jurisdictions` row to configure a custom map center. Only set coordinates after verifying the registered jurisdiction and its geographic center. The map has fallback centers for common Indian cities; stored database coordinates take precedence. GPS detection runs locally in the browser and selects the nearest active registered jurisdiction with a known center; CivicX does not send the user's coordinates to a geocoding service.
- The community feed supports one persistent upvote or downvote per signed-in user and discussion. The migration backfills vote counts from existing positive reactions and preserves `support_count` as the upvote total. The popularity sort uses net votes plus replies. The `civicx-community` bucket and its policies are not changed by the feature migration.
- Optional report photos are privacy-processed on-device, then compressed to JPEG and stored in the private `civic-report-attachments` bucket, restricted to the owning account. The optional Ask AI action sends only the locally redacted preview to the authenticated server-side AI route; its suggestion remains editable and is never saved automatically. A user can download a photo only while signed in.
- Signing out or clearing browser data does not delete database reports. The current schema intentionally uses restrictive account references: account deletion is not supported while civic reports or tracking records remain. Before introducing deletion, define an explicit retention/anonymization policy and operational workflow; do not delete the associated audit history.
- Configure and periodically verify Supabase database backups and point-in-time recovery according to the deployed plan, and test restoration. The migrations create the schema and access controls; they do not enable or verify a backup plan. Availability and recovery depend on the configured Supabase plan and operational backups.
- Acceptance check: create an account, submit multiple reports, sign out/close the browser, then sign in again and check **My reports**, including each report's full history and attachments. Repeat from another device using the same account. Also verify a second account cannot read the first account's rows.
- The repair migration grants citizens access only to their own report records and citizen history actions. New authority status changes, explicit reopenings, and evidence additions/removals are audited with the authenticated authority user's ID. Existing authority-history rows created by the earlier trigger may have no actor ID; the preflight reports their count, and those historical identities cannot be reconstructed automatically. Investigate them separately rather than fabricating attribution. The repair has not been applied or persistence-tested unless an operator has completed and documented the steps above.

## Weather and air quality

The homepage's Weather and Air Pollution / AQI cards open separate pages. They use live Open-Meteo forecast/geocoding and CAMS-model air-quality data through server routes. AQI is the provider's **US AQI estimate**, not CPCB National AQI and not a reading from an official monitoring station. Pages display the source, model timestamp, and that limitation. Geolocation is optional; city search is also available.

## Ads

Change campaigns only in `ads.config.json`. Each ad has `id`, `brand`, `type`, `file`, `link`, `headline`, `startDate`, `endDate`, `enabled`, and `weight`; the top-level `allowedPages` list controls where ads may render. The dashboard, community, AI, weather, and air-quality pages have dedicated left/right desktop rails. Both rails are hidden below 1,760px so they cannot obstruct mobile content. There are no in-feed, top-banner, popup, report-form, or tracking-page ads.

Samsung and Apple creatives are disabled placeholders, not endorsements, and are not rendered. Enable an ad only after its sponsor, creative, destination, and campaign dates are approved. Metrics are stored in the current browser's local storage, not a secured analytics backend. The Sponsor stats page is an unauthenticated prototype and must not be used as a production admin console.

## Report, AI, and CPGRAMS flow

- CivicX issue reports are account-scoped Supabase records with the truthful initial state **Prepared (awaiting user filing)**. CivicX does not submit to CPGRAMS or KMC. When a user saves a CPGRAMS reference from a report, the number is stored in the private `complaint_tracking` Supabase table only after email sign-in; row-level security limits access to that account. A typed number does not mark a report **Filed**.
- The Track complaint page looks up a signed-in user's saved reference and displays the status they recorded after checking the official CPGRAMS portal. No public CPGRAMS status API has been verified, so this is not an automatic or independently verified government status. The official status link remains available from CivicX.
- The optional photo helper posts only locally redacted JPEG `photos`, `note`, `city`, `mode`, and the selected issue `category` to `/api/ai/describe`; personal form fields and any other extra fields are rejected. The endpoint returns one JSON response. `GEMINI_API_KEY` is loaded only by the Node server from the ignored `.env` file and is never exposed to the browser.
- If the key is blank, the server logs a warning and AI endpoints return a configuration error; manual reporting still works.
- The CIVICX Assistant is available from the separate AI page after sign-in. It uses the server-only `GEMINI_API_KEY`, defaulting to `gemini-3.5-flash-lite` and trying `gemini-3.6-flash` only when the configured model is unavailable. Set `GEMINI_MODEL` in the server `.env` to select a different model supported by your Google AI API key; no Azure subscription is required. It supports multi-turn text chat through `/api/chat`. Recognized civic-issue keywords are answered from the user's text; other prompts are sent to Gemini as text only. Locally redacted photos are accepted as supporting evidence, validated in memory, and never forwarded to Gemini or stored. Recent text turns are held in the current tab's `sessionStorage` and cleared with **New chat**. Email addresses and phone numbers are redacted before text reaches Gemini. Do not share sensitive information. The assistant provides guidance only and cannot file complaints or verify official status. If the key is missing or Gemini fails, other text prompts report an error.
- The AI detector runs separate face and license-plate models locally in the browser. The original upload is decoded, inspected, and redrawn on a canvas; each detected region is permanently covered with an opaque block in the generated JPEG. The interface displays that processed photo, lets the citizen drag to cover additional regions, and requires review before upload. If the models, decoding, detection, or JPEG encoding fail, no image is uploaded and the manual report form remains available.
- Before Gemini, the existing endpoint validates actual JPEG bytes and metadata, then independently runs server-side YuNet face detection and the ONNX plate detector on the uploaded file. If either detector finds a region or verification fails, the request is rejected; no original-image fallback or client redaction flag is trusted. The browser sends the processed file bytes, never the source file. Detection is not perfect: missed small, obscured, distant, blurry, or unusual faces/plates remain possible, so citizens must review every preview and add manual covers.
- Model/runtime assets are served from CivicX itself after installation; image inference does not call an external detection service. The actual Gemini call still depends on provider availability and `GEMINI_API_KEY`.
- CPGRAMS public pages document registered-user filing and a returned registration number, but no public API specification was verified. API Setu's public directory search returned no CPGRAMS publishers/APIs during the official-source review. Consumer API access generally requires publisher approval; that platform guidance is not evidence that CPGRAMS has an API.
- KMC's official complaint procedure documents citizen-facing online complaint submission and a system-generated complaint number/status lookup, but no public KMC API contract was verified. West Bengal's Samashya Samadhan page does not document an API or a citizen complaint submission workflow. CivicX must obtain an official integration specification and authorization before automating any of these systems.
- CPGRAMS's public pages do not expose a downloadable issue-category catalog. The JSON registry therefore marks department routing as suggestions; it does not fabricate official category names.
- CPGRAMS says grievances sent by email are not entertained. Email delivery to a separate local authority is an adapter stub: no authority recipient or mail provider is configured, and no email is sent or logged as sent.
- The tracking page opens the official CPGRAMS status page. CAPTCHA/OTP and status checks remain on the authority's site; results saved in CivicX are labeled user-confirmed and unverified by CivicX.

Official integration research (checked 14 Nov 2026): [CPGRAMS Lodge](https://pgportal.gov.in/Home/LodgeGrievance), [CPGRAMS FAQ](https://pgportal.gov.in/Home/Faq), [API Setu CPGRAMS directory search](https://directory.apisetu.gov.in/search?q=CPGRAMS), [API Setu access flow](https://docs.apisetu.gov.in/document-central/explore-apisetu/Overview.html), [West Bengal Samashya Samadhan](https://wb.gov.in/samashya-samadhan.aspx), and [KMC complaint procedure](https://www.kmcgov.in/KMCPortal/jsp/ComplaintProcedure.jsp).

### Local photo privacy models

- Face detection: MediaPipe Tasks Vision with Google BlazeFace short-range and full-range models, run in the browser CPU delegate; the backend independently uses the MIT-licensed OpenCV Zoo YuNet ONNX model with ONNX Runtime Web/WASM. Both detectors return bounding boxes only; CivicX does not perform face recognition. Large photos are checked in overlapping crops.
- Number-plate detection: a separate YOLOv8n single-class plate-localization ONNX model, run locally with ONNX Runtime Web/WASM. Input photographs are tiled with overlap so more than one visible plate can be found; overlapping detections are merged.
- Browser face detector/runtime license: Apache-2.0. Server face model: MIT (license included in [assets/models/yunet-LICENSE](./assets/models/yunet-LICENSE)). ONNX Runtime Web: MIT. The selected plate model repository [declares MIT](https://huggingface.co/ml-debi/yolov8-license-plate-detection); its model card gives limited training provenance, so confirm the model author's licensing and provenance before commercial deployment. Its associated public dataset materials identify CC BY 4.0, but that does not independently establish the model's training lineage.
- Model files are stored under `assets/models`; their source URLs and hashes are documented in [assets/models/README.md](./assets/models/README.md).
- Browser validation detected multiple faces and plates in the tested samples, including a combined scene, and confirmed manual covers are included in the JPEG uploaded by the app. This is a limited sample, not an accuracy guarantee. Core bounding-box, tiling, JPEG metadata, fail-closed, and upload-path tests pass. The backend uses the official `@google/genai` SDK with non-streaming Gemini requests and a 60-second timeout. The configured model must be available to the server's Google AI API key; provider availability may vary.

## CPGRAMS browser extension

1. In Chrome or Edge, open the extensions page and enable **Developer mode**.
2. Choose **Load unpacked** and select the `extension` folder.
3. In CivicX, open one of your reports and choose **Copy all fields**.
4. Open the official CPGRAMS Lodge Public Grievance page, click the extension, paste the JSON, and choose **Fill fields**.
5. Review the fields, attach files manually if the portal accepts them, complete OTP/CAPTCHA yourself, and press Submit yourself.

The extension only fills a few matching fields on the CPGRAMS grievance form. It cannot safely set browser file inputs, solve verification, submit a form, or detect registration numbers reliably.

## Prototype limitations

- Sample city statistics and reports are illustrative, not official municipal data.
- Ad metrics remain local to the current browser. Reports and their audit histories require Supabase configuration and migrations; they are not available offline. Complaint references and user-confirmed tracking updates are private to the signed-in Supabase account when configured and the complaint-tracking migration has been applied.
- The community authentication and shared backend are inactive until a Supabase project and migration are configured as above.
- No real email transport, automatic CPGRAMS filing, CAPTCHA integration, automated status adapter, PWA/offline sync, or cross-device complaint tracking is configured.
